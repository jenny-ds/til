# 배포했더니 안되는 이유?

## 오늘 배운 것

- "내 컴퓨터에선 되는데 서버에선 안 된다"의 흔한 원인은 개발 환경과 배포 환경의 버전 불일치다.
- 패키지는 서로 의존성으로 얽혀 있고, 버전은 시맨틱 버저닝(MAJOR.MINOR.PATCH) 규칙으로 관리한다.
- 가상환경은 프로젝트별로 패키지를, 도커는 실행 환경 전체를 고정해서 버전 불일치를 막는다.

## 상세 내용

로컬에서 잘 돌아가던 코드가 배포하고 나면 안 되는 경우가 있다. 코드는 똑같은데 왜 안 될까?
대부분은 코드가 아니라 코드가 돌아가는 환경이 달라서 생기는 문제다.

우리가 작성하는 코드는 다른 사람이 만들어 둔 코드 묶음인 패키지를 가져다 쓰는데, 내 코드가 동작하려면 반드시 있어야 하는 패키지를 의존성이라고 한다.
그리고 그 패키지도 또 다른 패키지에 의존하기 때문에 의존성은 사슬처럼 이어진다.

패키지는 계속 업데이트되기 때문에 버전으로 구분하는데, 보통 시맨틱 버저닝 규칙을 따른다. '4.15.2'처럼 'MAJOR.MINOR.PATCH' 세 자리로 표기한다.

- MAJOR: 기존 기능이 깨질 수 있는 큰 변경
- MINOR: 기존 기능은 유지하면서 기능 추가
- PATCH: 버그 수정

만약 로컬에는 '2.1.0'이 설치되어 있는데 서버에서 새로 설치하면서 '3.0.0'이 깔리면, MAJOR 버전이 바뀌었으니 내가 쓰던 기능이 사라졌을 수 있다.
또 언어 자체의 버전이 다르거나, 로컬에만 설치하고 의존성 목록에 적지 않은 패키지가 있어도 서버에서는 에러가 난다.

그럼 필요한 패키지와 버전은 어디에 적어둘까?
Node.js에서는 package.json에 필요한 패키지 목록과 버전 범위를 적고, npm install로 한 번에 설치한다.
다만 범위로 적혀 있어서 설치 시점마다 다른 버전이 깔릴 수 있는데, 이를 막고 정확하게 동일한 버전을 설치하도록 기록해둔 파일이 package-lock.json이다.

위 내용처럼 환경으로 인한 문제가 생기는 케이스를 막을 방법이 있을까? 있다!
바로 가상환경과 도커다.
가상환경은 프로젝트마다 독립된 패키지 공간을 만들어서, 프로젝트 A와 B가 서로 다른 버전의 패키지를 써도 충돌하지 않게 해준다.
설치된 정확한 버전을 파일로 기록해 두면 다른 환경에서도 같은 버전을 설치할 수 있다.

```bash
python -m venv .venv
source .venv/bin/activate
pip freeze > requirements.txt
```

다만 가상환경은 패키지만 격리할 뿐, 언어 버전이나 OS 차이까지는 막지 못하기에, 도커를 사용한다.
도커는 실행 환경 전체를 컨테이너 하나로 묶어서 어디서 실행하든 같은 환경을 만들어준다.
